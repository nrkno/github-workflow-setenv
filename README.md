# github-workflow-setenv

Collects Terraform environment values from Vault and returns a short-lived Vault
wrapping token to the caller. The values themselves do not cross jobs as
workflow outputs.

## Caller requirements

- Grant the calling job `id-token: write`. This workflow does not check out
  source or need `contents: read` in the `setenv` job. The locked Vault action
  uses GitHub OIDC for `method: jwt`; other jobs in the caller may still need
  their own repository permissions.
- Pass `runs-on` as a JSON string or array inside the workflow input string,
  for example `runs-on: '"ubuntu-latest"'` or
  `runs-on: '["self-hosted","linux"]'`. Use a Linux runner with Docker, support
  for Node 24 actions, and `bash`, `curl` and `jq` on the host. The runner must
  reach Vault and the required container registry and credential endpoints.
- Set `eval: true` to include gathered variables in the wrapped payload. Pass
  a nonempty `role-name`. For the hardened setenv action, `azure: true` also
  requires nonblank `azure-tenant-id`, `azure-subscription-id`, and
  `azure-resource-group`. Review any custom Vault export names against the
  [setenv action's name rules](https://github.com/nrkno/github-action-setenv#security-notes).

## Migrate callers to pass the wrapping token as data

`setenv_outputs` is a **JSON-encoded wrapping token**, not the gathered values
or a shell expression. Treat it as a short-lived bearer credential. If a
caller puts the output expression directly in `run:`, move it to the consuming
step's `env:` mapping instead. For example, if the calling job ID is `setenv`:

```yaml
env:
  SETENV_WRAP_TOKEN: ${{ needs.setenv.outputs.setenv_outputs }}
```

Read the quoted `"$SETENV_WRAP_TOKEN"` variable as data. Decode it as JSON,
require a nonempty string, and stop without an unwrap request if the output
is missing or invalid. Unwrap it once against the same Vault before it
expires (`wrap-ttl` defaults to 300 seconds). Keep the handoff within trusted
jobs. Do not use `eval`, pass the token as a process argument, print it, or
put it in artifacts.

Moving the expression out of `run:` prevents it from becoming script text;
it does not hide the token from logs. The producer does not register a mask
for the wrapping token because the runner can drop masked job outputs. The
runner can also print the consuming step's environment before its script
starts, so masking on the first line is not enough. Verify with a synthetic
token on the target runner that the handoff stays out of logs, including the
step header. Do not promote a caller that cannot keep it private.

## Verification and release order

`python3 -I -B -m unittest discover -s tests -v` runs the workflow's wrap step
against a local fake Vault with real Bash, curl, and jq. It checks request
bytes, token output, error reporting and temporary-file cleanup. It does not
run a GitHub job or prove the OIDC policy, log masking, or cross-job transfer.

**Release blocker:** This branch still locks `github-action-setenv` to
`v3.2.1`. The hardened action is not published. Release that action first,
update the workflow's action version, regenerate `actions.lock`, and review
the new resolved SHA before promoting this workflow. Then verify the exact
pins with a trusted test caller on the intended self-hosted runner. Check
container startup, Vault OIDC with only `id-token: write`, runner masking of
synthetic values, cross-job delivery, and unwrap without leaking the token
or credentials. A local passing test cannot replace that run.

## Lockfile upkeep

`.github/workflows/actions.lock` is generated by the
[`gh actions-lock`](https://github.com/github/gh-actions-lock) extension. Step
`uses:` references keep full version tags (`actions/checkout@v7.0.1`); the
lockfile records the commit SHA each tag resolved to, including transitive
actions, and GitHub enforces those SHAs when the workflow runs. A moved or
re-pointed tag therefore cannot change what runs. Whenever a `uses:` reference
in `.github/workflows/` is added, removed or changed, update the lockfile in the
same PR:

```sh
gh extension install github/gh-actions-lock --pin v0.4.1  # once
gh actions-lock
```

Commit `actions.lock` together with any tag rewrite the extension makes.
Renovate regenerates the lockfile in its action-bump PRs; run the command above for hand edits.

Reusable workflow calls (`jobs.<job_id>.uses`) are not covered by the lockfile.
Keep them pinned to a full commit SHA with a `# vX.Y.Z` comment.
The `Actions lockfile` workflow runs `gh actions-lock --verify-local` on PRs that
touch `.github/workflows/` and fails if an action reference has no lockfile
entry. Do not edit the lockfile by hand.
